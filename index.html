모든 질문을 LLM에 보내지 않고, 질문 종류에 따라 길을 나눴습니다

어르신이 전화로 AI와 대화하는 서비스입니다. 모든 답을 LLM이 만들어 4~6초씩 걸려 통화처럼 느껴지지 않았습니다.

본인 기록이 필요한 질문"내가 어제 약을 먹었나?"RAG (LangChain)
날씨 질문"오늘 비 와?"외부 날씨 정보 연동
일반 지식 질문"머리 아플 땐 무슨 약?"LLM
응답 시간 (LLM 단독 대비)

4~6초 → 1~2초

50회 테스트에서 오류는 1~2회였고, 당시 서비스에 적용했습니다.

음성 인식 모델을 같은 기준으로 비교했습니다

평균 단어 오류율 (WER)
tiny1.025 base0.498 small0.856
평균 글자 오류율 (CER)
tiny1.35 base0.335 small0.793

Whisper tiny·base·small을 같은 문장으로 시험해 오류율을 비교했습니다. 낮을수록 정확합니다. 하나를 골라 파인튜닝까지 진행했지만, 서비스 적용은 보류됐습니다.

규칙이 끝없이 늘어나지 않도록 프롬프트를 네 층으로 설계했습니다

문제가 생길 때마다 프롬프트에 예시를 덧붙이면 규칙이 계속 늘어났습니다. 그래서 응답이 네 층을 차례로 거치는 구조와, 사용자 정보와 RAG 결과를 합쳐 통화마다 프롬프트를 만드는 구조를 설계했습니다.

사용자 발화"무릎이 너무 아파"

L1정체성
정해진 AI 페르소나로 응답합니다. 해요체, 따뜻한 톤.
L2판단 틀
"고통/불편" 감지 → 감성 우선 → 반드시 질문으로 끝내기
L3특수 상황
해당 없음. 일반적인 건강 이야기입니다.
L4품질 점검
질문으로 끝나는지, 따라 말하지 않는지, 1~2문장인지. 프롬프트를 고친 뒤 실제 통화로 확인했습니다.

최종 응답"저런, 비 오는 날이면 더 쑤시죠? 파스는 붙이셨어요?"

직접 만든 분류 모델을, 서비스 목적에 맞지 않아 빼자고 제안했습니다

만들었습니다

질문을 RAG로 보낼지 판단하는 문장 분류 모델을 만들었습니다.

따져 봤습니다

분류 단계가 추가되면서 응답이 다시 느려졌습니다. 필요한 판단은 RAG와 LLM 두 갈래뿐인데, 여러 카테고리로 먼저 나누는 구조라 단계가 과했습니다.

제안했습니다

팀장에게 먼저 의견을 말했고, 함께 대표에게 전해 서비스에 넣지 않기로 했습니다.
